# Upstream Feature Parity Matrix

This matrix compares the Android app with the authoritative `fork/deepseek-harness` source at baseline commit `39163dd30f`. The audit covered `packages/bundle/base/cordis.patch.yml`, `packages/bundle/base/package.json`, `packages/bundle/sdk-minimal/package.json`, `apps/cli/package.json`, `apps/desktop/package.json`, and the related implementation packages. The upstream default base profile includes Cordis Agents, session and JSONL persistence, model providers, approval, sandboxing, local tools, plugin management, plans and goals, jobs, skills, MCP, subagents and teams, web integration, and workspace services.

Statuses describe the Android implementation as it exists and has been exercised. “Partial” records a narrower implementation than the upstream behavior; “Not implemented” means the corresponding upstream feature is absent from this app. Device-tested original plugin packages are listed in [Plugin Compatibility](PLUGIN_COMPATIBILITY.md).

| Upstream capability | Android status | Android implementation and scope |
|---|---|---|
| DeepSeek Messages provider | Partial; upstream Cordis provider device-tested | The original `dsh-llm` and `dsh-llm-deepseek-api-key` packages registered and streamed a Messages request to an in-process loopback endpoint on an API 36 arm64 emulator. The app's provider behavior is not yet fully equivalent to every upstream request and error boundary; no live DeepSeek API request was part of that test. |
| Provider and model management | Partial | User-configured Messages-compatible URL and model ID; no upstream provider profiles, OAuth/account adapters, model catalog, or full pi-ai multi-provider configuration. |
| Credential management | Partial | One DeepSeek API key encrypted with Android Keystore; no upstream credential references, multiple accounts, or auth extensions. |
| Streaming and reasoning | Partial | SSE text and reasoning display with periodic checkpoints; upstream event, signature, usage, and error-boundary coverage is incomplete. |
| Agent and tool loop | Partial; original AgentLoop device-tested in an isolated harness | The product still uses Kotlin `HarnessEngine`. A separate API 36 arm64 instrumentation test loads the unmodified upstream `dsh-agent-loop`, submits a real Agent message, receives a loopback SSE response, and verifies original Session turn/message events. Production AgentLoop integration, its full hook behavior, and the provider-neutral model layer are not assembled. |
| Tool schemas and execution | Partial | Plugin schemas and calls use upstream `ctx.tools.schemas/execute`; Android file and shell tools are local adapters; the full upstream native/PTC executor and sandbox policy are not present. |
| Multiple sessions | Partial | Room isolates sessions, allows independent sessions to run concurrently, and blocks duplicate execution within a session; upstream lineage, fork, and query APIs are absent. |
| Concurrent tasks | Partial | Configurable concurrency is clamped to device resources; this is not the upstream Agent Team/task DAG and does not coordinate shared subagent work. |
| Cancellation, recovery, and retry | Partial | HTTP cancellation, shell process termination, exponential retry, and interrupted state after process death; there is no persistent task queue or resume-from-step execution. |
| Context management and compaction | Partial | Character-budget trimming occurs at turn boundaries; upstream token metering, compaction plugins, image offload, and tool-result pruning are absent. |
| Local workspace | Partial | App-private file operations and SAF single-file import/export; no arbitrary SAF tree mount, upstream workspace provider, or filesystem observation events. |
| File tools, search, and patching | Partial; original upstream read path device-tested | Original `dsh-fs-local`, `dsh-working-directory`, and `dsh-tool-fs` packages were installed and exercised together for UTF-8 reading, missing-path and invalid-offset errors, deactivation, and uninstall on API 36 arm64. That test disables `read_image`, `write`, `edit`, and `apply_patch`; filesystem watching, mutations, search, and broader approval/sandbox semantics remain incomplete or unverified. |
| Shell and terminal | Partial | `/system/bin/sh -c` under the app UID with working directory, stdin/stdout/stderr, exit code, timeout, and cancellation; no PTY, persistent shell, Bash profile, PowerShell, or desktop command environment. |
| Original Cordis plugin discovery and loading | Partial; representative packages device-tested | Original npm package/version or `.tgz` installation, upstream Cordis Loader and ESM contract, configuration, and Fiber lifecycle; five upstream plugin/service packages were exercised on an API 36 arm64 emulator. This is not the full base profile or plugin catalog. |
| Original plugin management and dependencies | Partial | On-device npm resolution, installation, enable/disable, JSON configuration validation, package replacement, uninstall, and Cordis Session persistence; no upstream marketplace/profile/bundle UI, configurable registry, automatic updates, publisher-signature verification, or complete `engines.dsh` management. |
| Original plugin runtime | Partial; arm64 emulator-tested | Javet Node Android i18n, Node ESM, npm, and Cordis Loader; real execution of `dsh-repeat-tool-reminder`, `dsh-tool-todo`, and the upstream filesystem read composition. Original DeepSeek Cordis provider routing and SSE were exercised against a test-only loopback endpoint. Other plugins, x86_64 native runtime, native addons, and platform-specific dependencies require separate compatibility work. |
| Original UI plugins | Partial; three Android device tests passed | Unmodified upstream React client fixtures install and execute locally through the original Cordis client loader and renderer. Verified layout-slot interaction, plugin configuration UI from the native manager, chat input activity, native draft insertion, deactivation, and uninstall. Only listed Android-hosted slots are mounted; the complete upstream client slot-owner tree is not. |
| Plugin permissions and isolation | Not implemented | Plugins share the app process and UID. There is no Node built-in restriction, per-plugin OS process, CPU/memory quota, signature trust root, or runtime capability enforcement. |
| Plugin async execution and lifecycle | Partial | Embedded Node bridge awaits Promises; Cordis Loader update/remove and Fiber disposal are exercised. There is no per-plugin stdout/stderr console or crash isolation. |
| Subagents and Agent Teams | Not implemented | No upstream child-Agent creation/recovery, delegation, shared task tree, or team tools. |
| Workflows and PTC | Not implemented | No upstream workflow system, Node PTC runtime, or reusable multi-tool workflow engine. |
| MCP clients, resources, and manager | Not implemented | No stdio/HTTP MCP transports, server lifecycle, resource access, or MCP tool discovery. |
| Web search, fetch, and browser use | Not implemented | No built-in search, fetch, or browser automation toolset. |
| Skills, personas, and presets | Not implemented | No upstream skill-file discovery/execution, Agent presets, or persona management. |
| Goals, plans, and TODO | Not implemented | No upstream goal persistence, plan mode, round driver, or complete TODO service. |

| Session logs and debugging | Partial | Room stores local per-session task/tool logs; original Cordis Session snapshots persist locally and restore after Node runtime recreation. There is no complete upstream event log, telemetry, or OpenTelemetry compatibility. |
| Session import and export | Partial | Local `deepseek-harness-mobile-session-v1` JSON format; upstream versioned JSONL formats are not supported. |
| Local persistence | Partial | Room stores app session/message/log/plugin rows; upstream storage domains, KV backends, and full schema migration are absent. |
| UI and settings | Partial | Native Compose screens for chat, sessions, plugins, workspace, logs, settings, and English/Simplified Chinese localization; original plugin UI contributions render through an embedded local client runtime on the tested slots. The complete upstream desktop client, command palette, session search, market, and profile editor are not present. |
| Attachments, images, and file references | Not implemented | Chat input is text-only; there is no upstream attachment store, image message flow, or reference parser. |
| Computer use and Office | Not implemented | No desktop GUI automation, window control, or Office toolset. |
| Remote API gateway and ACP | Not implemented | The Android app does not expose a remote Harness execution service or SDK JSON-RPC server. Local execution is retained on-device. |
| Telemetry and analytics | Not implemented | The app does not automatically upload usage data or product telemetry. |
| Automatic updates and plugin market | Not implemented | Users can enter an npm package specifier or select a local `.tgz`; there is no upstream plugin market search, bundle installation, or app/plugin auto-updater. |
| Legal notices | Implemented | The app exposes the project license and additional terms from Settings; third-party notices are included in the repository. |

## Upstream `dsh-base` profile audit

The upstream `packages/bundle/base/package.json` at the baseline commit declares **99 direct runtime dependencies**. `cordis.patch.yml` combines them into a profile rather than treating them as 99 independent tools.

| Upstream bundle/service area | Upstream functionality | Android implementation |
|---|---|---|
| Profiles, bundles, and patches | Cordis plugin-tree composition, profile layering, config overlays, HMR, and live plugin/config management | No complete profile/bundle composer; the app creates a limited Cordis context and loads original npm plugins through the upstream Loader. |
| Agent and instructions | Agent registry, default model, instructions, Agent loop, turn/step/request hooks, and user questions | Kotlin provides a limited multi-step loop and connects to Cordis Agent/Tools; the complete upstream Agent loop, instructions, and question flow are not assembled. |
| Parallel Agents and tasks | Subagents, in-process spawn/fork, Agent Teams, subagent control, goals, plan mode, and workflows/PTC | The complete upstream subagent, team tree, goal, and workflow runtimes are absent. |
| Models and LLMs | Generic LLM streaming, DeepSeek account/API extensions/API key, pi-ai providers, retry, and model selection | One Messages adapter and one API key with retry; the upstream provider/account profiles are not fully available. |
| Sessions, attachments, and context | Append-only Session events, JSONL persistence, projections/cache/query, SQLite search, titles, attachments, checkpoints, token meter, compaction, and spill | Room messages plus Cordis Session snapshots; the full upstream JSONL/query/attachment/token/compaction stack is absent. |
| Tool registration and commands | Tools service, native/PTC executor, Bash/PowerShell, working directory, shell environment, timeout policy, subprocess/jobs, TODO, and presentation | Upstream Cordis tools are used for plugins; Android-private filesystem and `/system/bin/sh` adapters are local. Desktop Bash/PowerShell/PTC/jobs are absent. |
| Filesystem and sandbox | Local filesystem, filesystem observation, sandbox, permission presets, approval, and policy | App workspace path checks and per-call approval exist; the upstream sandbox policy and full isolation are not present. |
| Network and external integrations | Web fetch/search, MCP resources, API Gateway/remote access, and OpenTelemetry | Model API and explicit plugin network requests are supported; the complete upstream client/server/telemetry ecosystem is absent. The app does not provide remote Harness execution. |
| Accounts, settings, and persistence | Authorization, credentials, settings, storage hub/JSON/domain backend, plugin inventory, and market | One provider's Keystore credential, Room, and app-private files; no full upstream account system, storage domains, or plugin market. |

This inventory is based on the upstream `dsh-base` dependency set and patch rows. Each row summarizes a feature area; it does not imply that every listed package can be enabled on Android. Plugin package compatibility is described separately in [Plugin Compatibility](PLUGIN_COMPATIBILITY.md).
